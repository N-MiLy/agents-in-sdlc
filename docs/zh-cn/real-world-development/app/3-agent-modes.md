我们先为项目添加了一项小功能。但较大的更改需要更完善的流程。GitHub Copilot app 可以融入组织现有的工作流，帮助我们用正确的方式构建正确的内容。接下来的几课将介绍典型的智能体驱动开发流程：从议题着手实现新功能，确保代码有效、功能符合预期，最终成功合并到项目中。

> [!NOTE]
> 继续完成此功能工作流时，你会使用同一个会话。通常，不同类型的文件会放在不同会话或 PR 中处理；这里为聚焦核心概念，我们会简化流程。

在本课中，你将：

- 根据 GitHub 议题开始新的智能体会话。
- 在 **Plan** 模式中定义需求。
- 使用 **Autopilot** 模式实现新功能。
- 审查代码。
- 在浏览器画布中手动验证功能。

继续实现此功能时，你还将更新存储库指令、自定义现有的 quality-checks 技能、添加 MCP 验证、创建 QA 智能体，并创建功能 PR。

## 场景

Tailspin Toys 的游戏目录不断扩大，访客需要按类别和发行商筛选游戏。待办事项中的议题描述了此功能，但组合类别等细节需要在编码前达成一致。你将使用 Plan 模式确定这些决策，然后授权 Autopilot 在明确的范围内实现功能。

## 背景

将 AI 编码智能体引入开发流程，并不会改变基本原则。事实上，这些原则变得更加重要！大多数开发者遵循的流程大致如下：

1. 打开一项已创建的议题，查看其中关于待完成工作的详细信息。
2. 制定构建内容的计划。
3. 编写并审查代码。
4. 运行测试以验证代码。
5. 手动验证新功能。
6. 创建拉取请求 (PR)。
7. 代码经过审查且持续集成流程成功后，合并代码。

> [!NOTE]
> 具体流程会因团队和组织而异，但大多数流程都与上述做法类似。

遵循这种标准流程，可以确保 AI 生成的代码符合既定需求，并接受与手写代码相同的审查。

## 会话模式

**会话模式**决定智能体拥有多少自主权。你可以通过提示框下方的下拉列表设置模式，并随时更改：

- **Interactive：**你与智能体协作。智能体提出更改建议，并等待你的输入后再继续。
- **Plan：**智能体先创建计划。你审查并批准计划后，智能体才会执行。
- **Autopilot：**智能体完全自主工作——编写代码、运行测试并不断迭代，无需等待输入。

先在 Plan 模式中开始并审查计划，然后使用 Autopilot 实现计划。

## 从议题开始会话

开始前，确认星级评分 PR 已合并，并且本地 `main` 是最新版本。

1. 在侧边栏的 **Sessions** 下，选择 Tailspin Toys 存储库文件夹，然后在存储库顶部导航中选择 **Issues**。打开 **Allow users to filter games by category and publisher**。这是已有的预置议题，无需再创建一个。
2. 选择 **New session**，并基于更新后的 `main` 选择**新工作树**。

    ![GitHub Copilot app 中的议题视图，箭头指向 New session 按钮](../../../_images/app-new-session-from-issue.png)

3. 确认该议题已关联到会话，然后在模式选择器中选择 **Plan**。

> [!NOTE]
> 如果找不到 Node.js 或 npm，请让智能体运行 `node --version` 和 `npm --version`。如果这些命令在终端中正常运行，但在会话中失败，请检查 app 的 PATH 或版本管理器设置，然后完全退出并重新打开 app。重试失败的操作和检查；不要仅仅因为智能体找不到 npm 就重新安装 npm。

## 规划筛选功能

规划可以让你在 Copilot 编写代码前审查实现方案。由于你从议题开始会话，Copilot 已经获得功能请求作为上下文。发送以下提示：

```plaintext
Build this feature.
```

回答 Copilot 的问题，并将计划与议题的验收标准进行比较。确认计划涵盖类别和发行商筛选、无障碍控件、数据访问更改和测试。讨论任何不明确的行为，例如如何组合多个类别，或没有游戏匹配时应如何处理。

计划应包括使用项目现有工具运行 lint、单元测试、端到端 (E2E) 测试和类型检查。计划应聚焦于实现并测试筛选功能；完成质量工作流后再创建 PR。批准计划前，请先要求修改任何不妥之处，并记下议题 URL 及商定的澄清内容，以便之后验证。

## 明确批准 Autopilot

对计划满意后，选择 **Approve and implement this plan**，或当前版本中含义相同的选项。请确认当前激活的模式，而不要假设批准计划会自动切换模式。确认模式指示器显示 **Autopilot**。

Copilot 会开始实现功能！你会看到它根据既定计划不断迭代、生成代码并运行测试。

> [!NOTE]
> 批准后可能会立即开始实现，因此请先审查计划。如果 Copilot 报告缺少依赖项或端口冲突，请先解决设置问题，再将检查视为已完成。只停止由你启动的服务器。

## 审查并验证实现

代码生成后，和其他代码一样，需要在合并前审查。我们一起审查代码并运行网站，确认一切正常。

1. 打开 **Changes**，检查筛选功能的实现和测试。
2. 根据议题和已批准的说明比较实现结果，包括多个类别和发行商组合。检查更改是否遵循现有存储库指令。
3. 检查 lint、单元测试、E2E 测试和类型检查的输出。跳过的检查不算通过。
4. 解决失败项并重新运行受影响的检查，然后再接受实现。Playwright 的 E2E 配置会构建并提供预览，也可能复用本地服务器；确认被测服务器属于当前工作树，而不是之前课程启动的服务器。

## 体验新功能

代码看起来不错——但能运行吗？像之前一样启动应用，然后在浏览器画布中打开网站。

1. 使用以下提示，请 Copilot 启动应用并在浏览器画布中打开页面：

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. 片刻之后，应用会启动，Copilot app 中会打开浏览器窗口。
3. 选择一个类别并确认结果符合类别条件。清除筛选后，选择一个发行商并确认结果符合该发行商条件。
4. 同时使用类别和发行商筛选，并根据议题和已批准的计划比较结果。如果支持多个类别，还要验证是否按约定的方式组合。
5. 尝试筛选出没有匹配游戏的组合并检查空状态。清除或重置筛选条件，确认完整列表会重新显示。
6. 完成后，使用以下提示请 Copilot 停止它为此会话启动的开发服务器：

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 为后续课程保留此会话

暂时不要创建或合并筛选 PR。保留此会话、工作树和分支，供第 4 到第 8 课继续使用。接下来，你会将自定义指令应用于筛选代码，然后添加技能和 QA 改进，最后在第 8 课中创建并合并合并后的 PR。停止开发服务器后，可以让会话保持闲置状态；下一课中请返回同一会话。

## 总结和后续步骤

你已使用不同的智能体模式构建并审查一项功能。在本课中，你：

- 根据 GitHub 议题开始了新的智能体会话。
- 在 **Plan** 模式中定义了需求。
- 使用 **Autopilot** 模式实现了新功能。
- 审查了代码。
- 在浏览器画布中手动验证了功能。
